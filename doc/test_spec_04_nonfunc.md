## 1. テスト方針

非機能テストは機能の正しさではなく、品質特性（セキュリティ・性能・ユーザビリティ・互換性）を検証する。

### 1-1. テストケース記述凡例

| 列名 | 説明 |
|------|------|
| テストID | `NFT-カテゴリ-連番`（例：NFT-SEC-001） |
| テスト観点 | 確認する品質特性 |
| テスト内容 | 実施する検証の内容 |
| 合格基準 | 合格とみなす条件 |
| 優先度 | 高／中／低 |

## 2. セキュリティテスト

### 2-1. 認証・認可

| テストID | テスト観点 | テスト内容 | 合格基準 | 優先度 |
|----------|-----------|---------|---------|--------|
| NFT-SEC-001 | 未認証アクセス拒否 | ログインせずに `/daily-reports` などの保護されたURLへ直アクセスする | ログイン画面へリダイレクト、またはHTTP 401が返る | 高 |
| NFT-SEC-002 | 他ユーザーの日報へのアクセス | USER-01で認証後、USER-02の日報IDをURLに指定してアクセスする | HTTP 403 が返り、データが取得できない | 高 |
| NFT-SEC-003 | 他ユーザーの日報の更新 | USER-01のトークンで `PUT /daily-reports/{USER-02の日報ID}` を呼び出す | HTTP 403 が返る | 高 |
| NFT-SEC-004 | ロール昇格の拒否 | 営業ロールのトークンで `DELETE /customers/{id}` を呼び出す | HTTP 403 が返る | 高 |
| NFT-SEC-005 | JWT改ざんの拒否 | JWTのペイロード部分を Base64 でデコードし、`role` を `admin` に書き換えて再エンコードしたトークンでアクセスする | HTTP 401 が返る | 高 |
| NFT-SEC-006 | トークン期限切れ後のアクセス | 有効期限が切れたトークンを使用してAPIにアクセスする | HTTP 401 が返り、`error.code: "SYS-003"` が含まれる | 高 |

### 2-2. 入力値のサニタイズ

| テストID | テスト観点 | テスト内容 | 合格基準 | 優先度 |
|----------|-----------|---------|---------|--------|
| NFT-SEC-010 | XSS（格納型） | 訪問内容に `<script>alert('XSS')</script>` を入力して保存し、詳細画面で表示する | スクリプトが実行されず、テキストとしてエスケープされて表示される | 高 |
| NFT-SEC-011 | XSS（顧客名） | 顧客名に `<img src=x onerror=alert(1)>` を入力して保存し、一覧画面で表示する | スクリプトが実行されない | 高 |
| NFT-SEC-012 | SQLインジェクション | 顧客名検索キーワードに `'; DROP TABLE customers; --` を入力して検索する | エラーなく空の検索結果が返り、データが破損しない | 高 |
| NFT-SEC-013 | 大量データ送信（ペイロード） | 訪問内容に100万文字のデータを含むリクエストを送信する | HTTP 400 または 413 が返り、サーバーが正常稼働を続ける | 中 |

### 2-3. 通信セキュリティ

| テストID | テスト観点 | テスト内容 | 合格基準 | 優先度 |
|----------|-----------|---------|---------|--------|
| NFT-SEC-020 | HTTPS強制 | HTTP（非暗号化）でAPIエンドポイントにアクセスする | HTTPSへリダイレクトされる、またはHTTP 301/302が返る | 高 |
| NFT-SEC-021 | パスワードのハッシュ化 | DBに格納されたパスワードのフィールドを確認する | パスワードが平文で保存されていない（bcrypt等でハッシュ化されている） | 高 |
| NFT-SEC-022 | レスポンスへのパスワード非含有 | `GET /salespeople/{id}` のレスポンスを確認する | `password` フィールドがレスポンスに含まれない | 高 |

### 2-4. ブルートフォース対策

| テストID | テスト観点 | テスト内容 | 合格基準 | 優先度 |
|----------|-----------|---------|---------|--------|
| NFT-SEC-030 | ログイン試行回数制限 | 誤ったパスワードでログインを連続して10回試みる | 一定回数以上でアカウントロックまたはレート制限（HTTP 429）が発動する | 中 |

## 3. パフォーマンステスト

### 3-1. レスポンスタイム

各APIの単体レスポンスタイムを計測する。テスト環境はステージング環境（本番相当のDBレコード数）で実施。

| テストID | テスト対象API | テスト内容 | 合格基準 | 優先度 |
|----------|------------|---------|---------|--------|
| NFT-PERF-001 | `POST /auth/login` | 単一リクエストのレスポンスタイムを計測 | 2,000ms 以内 | 高 |
| NFT-PERF-002 | `GET /daily-reports` | 100件の日報が存在するユーザーで計測 | 1,000ms 以内 | 高 |
| NFT-PERF-003 | `GET /daily-reports/team` | 部下5名・各100件の日報が存在する状態で計測 | 1,500ms 以内 | 高 |
| NFT-PERF-004 | `POST /daily-reports` | 訪問記録10件を含む日報作成リクエストを計測 | 2,000ms 以内 | 中 |
| NFT-PERF-005 | `GET /customers/select-options` | 顧客マスタに1,000件存在する状態で計測 | 500ms 以内 | 中 |

### 3-2. 同時接続テスト

| テストID | テスト内容 | 合格基準 | 優先度 |
|----------|---------|---------|--------|
| NFT-PERF-010 | 10ユーザーが同時にログインを試みる | 全ユーザーが5,000ms 以内にレスポンスを受信し、エラーが発生しない | 中 |
| NFT-PERF-011 | 10ユーザーが同時に日報を作成する（各自異なるユーザー・日付） | 全リクエストが成功（201 Created）し、データの整合性が保たれる | 中 |
| NFT-PERF-012 | 5ユーザーが同一日付・同一ユーザーの日報を同時に更新しようとする（下書き状態） | 1件のみ成功し、残りは409または整合性エラーが返る | 中 |

## 4. ユーザビリティ・アクセシビリティテスト

### 4-1. ユーザビリティ

| テストID | テスト観点 | テスト内容 | 合格基準 | 優先度 |
|----------|-----------|---------|---------|--------|
| NFT-UX-001 | エラーメッセージの視認性 | バリデーションエラー発生時に、エラーが発生したフィールドの近くにメッセージが表示されるか確認する | エラーフィールドに赤枠が表示され、フィールド直下に赤字でメッセージが表示される | 高 |
| NFT-UX-002 | フォームの入力補助 | 日報作成画面で訪問記録を3行追加し、2行目を削除してから提出する | 削除操作・並び替えが直感的に実施でき、操作後の表示順が正しい | 中 |
| NFT-UX-003 | トースト通知の可視性 | 保存成功・失敗時にトーストが適切に表示されるか確認する | 画面右上にトーストが表示され、成功時は緑・エラー時は黄または赤で区別される | 中 |
| NFT-UX-004 | 非活性ボタンの視覚的区別 | 訪問記録0件の日報作成画面で「提出する」ボタンが非活性であることを確認する | 非活性状態のボタンがグレーアウトなど視覚的に区別できる | 中 |
| NFT-UX-005 | 確認ダイアログの動作 | 顧客削除時に確認ダイアログが表示されることを確認する | 削除前にダイアログが表示され、「キャンセル」で削除が中止される | 高 |

### 4-2. アクセシビリティ

| テストID | テスト観点 | テスト内容 | 合格基準 | 優先度 |
|----------|-----------|---------|---------|--------|
| NFT-A11Y-001 | キーボード操作 | マウスを使わずTabキーのみで日報作成フォームを操作し、提出できるか確認する | Tabキーでフォーカス移動でき、Enterキーでボタン操作ができる | 中 |
| NFT-A11Y-002 | フォームラベルの関連付け | 各入力フィールドにラベルが適切に関連付けられているか確認する（HTMLの `for`/`id` 属性） | スクリーンリーダーでフォームを操作した際に各フィールドの名称が読み上げられる | 中 |
| NFT-A11Y-003 | エラーメッセージの通知 | バリデーションエラー発生時にスクリーンリーダーで内容が伝わるか確認する | `aria-describedby` または `role="alert"` を使用してエラーが通知される | 低 |

## 6. 回帰テスト方針

機能追加・バグ修正のリリース時に実施する回帰テストの範囲を定義する。

### 6-1. 回帰テストの範囲

| トリガー | 実施範囲 |
|---------|---------|
| 日報機能の変更 | SCN-01〜02（E2Eシナリオ）＋ API-RPT-xxx・API-VIS-xxx の全件 |
| コメント機能の変更 | SCN-01・SCN-03＋ API-CMT-xxx の全件 |
| マスタ機能の変更 | SCN-04・SCN-05＋ API-CUST-xxx・API-SALES-xxx の全件 |
| 認証・権限の変更 | SCN-06（アクセス制御）＋ API-CMN-xxx・API-AUTH-xxx の全件＋ NFT-SEC-001〜006 |
| 全体リリース | 全テストケースの「優先度：高」を実施 |

### 6-2. 自動化推奨テスト

以下は自動テスト（CI/CDパイプライン組み込み）への移行を推奨する。

| カテゴリ | 対象テストID |
|---------|------------|
| APIテスト（全件） | API-AUTH-xxx、API-RPT-xxx、API-VIS-xxx、API-CMT-xxx、API-CUST-xxx、API-SALES-xxx |
| バリデーションテスト | LOGIN-010〜022、REDIT-040〜047、CUST-011〜013、SALES-011〜015 |
| セキュリティテスト | NFT-SEC-001〜006（認証・認可）、NFT-SEC-010〜013（入力値） |

## 7. テスト完了基準

### 7-1. リリース判定基準

以下の基準をすべて満たした場合にリリース可とする。

| 基準 | 目標値 |
|------|--------|
| 優先度「高」のテストケース消化率 | 100% |
| 優先度「高」の合格率 | 100% |
| 優先度「中」のテストケース消化率 | 95% 以上 |
| 優先度「中」の合格率 | 95% 以上 |
| セキュリティテスト（NFT-SEC）合格率 | 100% |
| 未解消バグ（優先度高） | 0件 |
| 未解消バグ（優先度中） | 3件以下（ただし業務影響なし・回避策あり） |
